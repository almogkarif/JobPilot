## Verification and resource impact

Production routing is provided by `ISRAELI_FINAL_ROUTES` and `collect_israeli_final()` in `app/collectors/israeli_recovery_final.py`. Discount reuses the existing Oracle CX reader. Redmatch uses the exact employer tenant, public country filter, full description and real `compPositionID`. HOT preserves its real shared board with narrowly validated record metadata. IEC binds its embedded full payload to matching live cards, IDs, regions, links and unexpired deadlines. Fox details require matching IDs and per-role city.

All six collectors passed `validate_source_payload` against current public responses. Focused tests: **96 passed, 0 skipped** (`tests/test_israeli_recovery_final.py`, `tests/test_israeli_boards.py`, `tests/test_source_quality.py`). The full suite and shared integration checks belong to the root agent.

Worst case per aggregate scan: **87 public requests**, **880 normalized rows**, **4,000,000 response bytes per request**, **24,000 description characters per row**, and **four concurrent details per board**. Redmatch input is limited to 1,000 rows per response; output is limited to 200. Production requests reject redirects. At hourly scheduling this is 2,088 requests/day and 62,640/30 days; the deliberately pessimistic external body ceiling is 348 MB/scan, 8.352 GB/day and 250.56 GB/30 days. This traffic comes from employer services, not Supabase.

These collectors add zero database or Storage queries and zero direct Supabase egress. Existing shared catalog projection and 64 MiB/day reservation controls continue to govern persistence; no bulk scan was initiated. Root owns the egress regression and final integration gates.

Detailed checked URLs, statuses, body sizes, hashes, sample IDs, withheld IDs, and per-source reasons are in [the JSON audit](source_alternatives_israeli_2026-09-27.json). Search-indexed or aggregate content was used for discovery only and was never promoted into a live verified vacancy payload.
